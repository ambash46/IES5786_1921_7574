שלב1 - פרימיטיביםוגופים גיאומטריים 
 
בשלב הראשון של הפרויקט נבנה את התשתית המתמטית והגיאומטרית שעליה יתבסס מנוע הרינדור בהמשך הקורס. 
נממש את הפרימיטיבים  הגיאומטריים הבסיסיים (נקודות, וקטורים וקרניים), נגדיר מחלקות עבור גופים גיאומטריים 
שונים, ונבדוק את פעולות הפרימיטיבים באמצעות תוכנית בדיקה ראשית. 
חשוב להקפיד על מימוש מדויק ויעיל כבר בשלב זה, משום שכל החישובים הגיאומטריים בהמשך הפרויקט נשענים על 
מחלקות אלו. 
 
לפני תחילת ביצוע ההנחיות יש ללמוד את המצגת של השלב. חלק מהמידע המוזכר בהנחיות מופיע במצגת הזו.

4. עקרונות מימוש כלליים 
אובייקטים בלתי נתונים לשינוי (Immutable Objects) 
כל האובייקטים של הפרימיטיבים ושל הגופים הגיאומטריים יהיוimmutable .כלומר: 
• כל השדות יוגדרו final 
• אין מתודות שמשנות מצב 
• כל פעולה מחזירה אובייקט חדש. 
גישה זו מפחיתה תקלות ומבטיחה יציבות בהמשך הפרויקט. 
 
שימוש ב-final 
יש להקפיד על הכללים הבאים: 
• כל מחלקה שאין ממנה ירושה תוגדר final 
• במחלקות אב, מתודות שאין צורך לדרוס במחלקות יורשות יוגדרוfinal 
מטרה: 
• למנוע דריסה בטעות 
• לשמור על יציבות הארכיטקטורה 
 
שימוש במחלקת Util 
בפרויקט זה אין להשוות מספרים ממשיים ל-0 באמצעות== או אופרטורים של השוואה יחסית, כגון > 
וכדומה. במקום זאת יש להשתמש במתודות: 
• Util.isZero(...) 
• Util.alignZero(...) 
מתודות אלו מטפלות בשגיאות עיגול של חישובי נקודה צפה. 
 
עקרון DRY 
יש להימנע משכפול קוד. בפרט: 
• יש להשתמש במתודות של Double3 
• ישלהשתמש במתודות קיימות במקום לחשב שוב 
• אין להעתיק נוסחאות בין מחלקות 
 
הנחיות נוספות 
• יש להוסיף לכל המחלקות, השדות והמתודות תיעוד בפורמט JavaDoc – ראה במצגת השלב ובנספחB 
• יש להקפיד על דרישות עיצוב קוד ומוסכמות שמות– ראה במצגת השלב ובנספח C 
• אין להגדיר מתודות אחזור (גטרים) בשלב הזה,  למעט מחלקת Ray 
• אין להגדיר מתודות עדכון (סטרים) בכלל 
• כל שדות המופע שהרשאה שלהם לא מוזכרת בהמשך – פרטיים (private), למעט שדות קבועים המוזכרים 
בהמשך – ההרשאה שלהם ציבורית (public) 
• כלהבנאים והמתודות שעליכם להגדיר – עם הרשאה ציבורית (public), אלא אם נאמר אחרת במפורש 
• דריסת מתודה השוואה (equals) לפי הכללים והקוד המופיע במצגת השלב

לצורכי דיבוג)

o עיקרוןDRY וביצועים (ביטוי שיש יותר משימוש אחד בו 
o שיפור קריאות (מניעת ביטויים ארוכים מדי)

9. טעויות נפוצות 
יצירת Vector עם שדה נוסף מחלקת Vector יורשת מ-Point ולכן משתמשת בשדה_xyz של מחלקת האב. 
אין להוסיף שדה נוסף עבור הקואורדינטות. 
שימוש ב-Math.pow לחישוב
ריבוע 
אין להשתמש במתודה  Math.pow(x,2) לחישוב ריבוע. יש לחשב ריבוע באמצעות 
מכפלה: x * x 
יצירת אובייקטים זמניים לצורך
חישובים 
אין ליצור אובייקטים זמניים לצורך חישובים. לדוגמה, אין לחשב מרחק כך: 
p1.subtract(p2).length() 
בדיקות מיותרות של וקטור אפס אין צורך לבדוק יצירת וקטור אפס בתוך פעולות וקטוריות. אם פעולה יוצרת 
וקטור אפס, החריגה תיזרק אוטומטית ע"י הבנאי של Vector. 
שינוי אובייקטים קיימים כל המחלקות בפרויקט הן immutable .לכן אין לשנות שדות של אובייקטים
קיימים — כל פעולה מחזירה אובייקט חדש. 
שימוש במתודות טריגונומטריות פעולות על וקטורים צריכות להתבסס על נוסחאות של אלגברה לינארית בלבד. 
אין להשתמש בפונקציות טריגונומטריות. 
מימוש מחדש של subtract 
במחלקת Vector 
המתודה subtract כבר ממומשת במחלקת Point ולכן אין לממש אותה מחדש
במחלקת Vector. 
שינוי הרשאות שדות כדי “לפתור
שגיאת קומפילציה 
אין לשנות הרשאות גישה של שדות או מתודות כדי לעקוף שגיאת קומפילציה. 
לדוגמה, אם קוד אינו מתקמפל בגלל גישה לשדה כמו _direction או _xyz ,אין
לשנות את ההרשאה של השדה ל-public .שינוי כזה בדרך כלל מסתיר את הבעיה 
האמיתית וגורם להפרת דרישות התרגיל (כגון immutability או encapsulation .)
יש לשמור על הרשאות הגישה כפי שמוגדר בהנחיות ולתקן את הקוד בהתאם. 
משל להשתמש בגטר כפי שמוגדר במחלקה Ray.

הפרויקט בקורס אינו משתמש במנגנון Java modules .לכן כשאתם פותחים פרויקט Java חדש עבור הקורס: 
• אין להשתמש במודולים בפרויקט 
• אין ליצור קובץ module-info.java 
• אין להשתמש בהגדרות module במערכת הבנייה 
הסיבה לכך היא ש-Java אינה מטרת הקורס, והשימוש במודולים (ובמיוחד תלויות בין מודולים) מוסיף מורכבות
שאינה נדרשת בפרויקט. הקוד בפרויקט בנוי במבנה packages רגיל בלבד. 
בעת יצירת הפרויקט יש לוודא שלא נוצר הקובץ module-info.java: 
Eclipse IntelliJ IDEA 
בחלון יצירת פרויקטיש להסיר את הסימון 
של: Create module-info.java 
בחלון יצירת פרויקטאין לבחור פרויקט 
מסוג Java module 
אם נוצר module-info.java בטעות ה-IDE עלול להציג שגיאות קומפילציה כגון: 
• package primitives is not visible 
• package geometries is not visible 
• module does not read another module 
• או שגיאות import בין החבילות 
פתרון 
1. למחוק את הקובץ module-info.java 
2. לבצע Rebuild Project 
לאחר מחיקת הקובץ הפרויקט יחזור למצב עבודה רגיל.

A.4 פירמוט ידני של הקוד 
לעיתים נדרש לפרמט קוד ידנית באמצעות ה-formatter של סביבת הפיתוח. פעולה זו מתקנת באופן אוטומטי: 
• הזחות 
• רווחים סביב אופרטורים 
• מבנה בלוקים וסוגריים 
• סגנון כללי של הקוד 
קיצורי המקשים לפירמוט: 
ניתן להפעיל פירמוט על מספר קבצים או על כל קוד המקור בפרויקט. יש לבחור ב-IDE את התיקייה src .לאחר
מכן יש להפעיל את קיצור הפירמוט. ה-IDE יבצע פירמוט על כל קבצי הקוד שבתיקיית src. 
נ.בחשוב לבחור את תיקיית src בלבד ולא את כל הפרויקט, כדי להימנע מפירמוט קבצים שאינם קוד מקור, כגון
קבצי תיעוד שנוצרים בתיקייה doc . 
לפני יצירת תג ההגשה tag) לפרויקט מומלץ לבצע: 
• פירמוט לכל קוד המקור על ידי בחירת תיקיית src 
• שמירת כל הקבצים 
• commit  ו-push של השינויים 
פעולה זו מבטיחה שכל הקוד בפרויקט עומד במוסכמות הפורמט של הקורס.

נספח C – מוסכמות קוד (Coding Conventions) 
מוסכמות קוד אחידות הן חלק מדרישות הקורס. 
 
C.1 מוסכמות שמות 
רכיב פורמט 
Classes PascalCase 
Methods camelCase 
Variables camelCase 
Parameters camelCase 
Instance fields _fieldName 
Static fields s_fieldName 
Constants UPPER_CASE 
 
C.2 עיצוב 
עבור סוגריים מסולסלות יש להשתמש בסגנון Java: 
if (condition) { 
    doSomething(); 
} else { 
    doSomethingElse(); 
} 
יש להקפיד על: 
• הזחה תקינה 
• רווחים סביב אופרטורים 
• שורת רווח אחת בלבד ברצף 
ראה בעניין הפירמוט בנספח A. 
 
C.3 כתיבתתיעוד Javadoc 
יש לכתוב Javadoc לפני: 
• כל מחלקה 
• כל שדה 
• כל מתודה 
אין לכתוב Javadoc עבור: 
• מתודות Override 
• מימושים של מתודות interface 
התיעוד חייב להיכתבבאנגלית בלבד. 
יש ליצור ולכתוב תיעוד Javadoc מיד לאחר הגדרת כותרת המחלקה, מיד לאחר הגדרת כותרת המתודה, מיד
לאחר הגדרת שדה.
